# 第三阶段：运营指标计算说明

验证日期：2026-10-18。环境：Windows、Python 3.13.2。当前仅使用虚构模拟数据。

## 1. 程序怎样工作

可以把过程理解为“先检查整张订单表，再分别整理订单和商品，最后显示答案”：

1. `metrics.calculate_metrics(path)` 调用已有的 `order_validator.load_and_validate(path)`，后者调用已有 CSV 读取模块。编码、字段、金额、状态及跨行一致性规则全部复用，没有另写一套宽松规则。
2. 任意一项校验失败，直接抛出原有 `CsvValidationError`，不返回报表或部分合格数据。命令行显示具体物理行号、字段和原因，退出码为 1。
3. 全部通过后，只汇总“已支付、已全额退款、部分退款”三种状态的行。未支付、已取消不贡献支付、退款和成交件数。
4. 金额按商品明细已经分摊好的份额相加；订单按唯一 `order_id` 汇总，商品按 `product_id` 汇总。
5. `report_metrics.py` 显示中文结果，成功退出码为 0；不写入任何 CSV、数据库或报表文件。导入两个新模块也不会自动读取订单或计算。

`metrics.py` 保存计算结果，`report_metrics.py` 负责文字展示。结果和商品条目采用不可变数据对象，防止展示过程不小心改掉金额；这不是数据库或额外的业务框架。

## 2. 四类核心指标的公式

下表的“已支付类”均包含后来全额、部分退款的订单。退款列是已完成退款，不包含申请中金额。

| 指标 | 当前公式及边界 |
| --- | --- |
| 支付金额 | 已支付类明细的 `payment_amount` 合计；全额退款订单仍保留历史支付 |
| 退款金额 | 同一范围的 `refund_amount` 合计；不再次扣除已被删除的订单，避免重复扣减 |
| 净销售额 | 支付金额 − 退款金额 |
| 支付订单数 | 已支付类中唯一订单编号数；同一订单有多少商品行都只计一笔 |
| 净有效订单数 | 上述订单分别汇总后，整单支付 − 整单退款大于零的订单数 |
| 支付客单价 | 支付金额 ÷ 支付订单数，包括全额退款订单的历史支付和订单数 |
| 净客单价 | 净销售额 ÷ 净有效订单数，排除净金额为零的全额退款订单 |
| 商品净成交件数 | 按商品编号汇总已支付类购买数量，再减去明确的 `refund_quantity` |
| 商品净销售金额 | 同商品编号的支付合计 − 已明确归属该商品明细的退款合计 |

商品榜按净成交件数降序；并列时按商品编号的**字符串升序**，不依赖输入行顺序。例如 `P10` 在 `P2` 之前；本样本使用补齐编号 `P001` 等。相同名称但不同编号不会合并。

只退差价时，明确记录 `refund_quantity = 0`：扣退款金额，不扣件数。缺失退款件数必须报错，不能猜成零，也不能用退款金额除单价反推数量。

净有效订单看的是整单净金额，不要求剩余件数大于零。例如“全部商品退回，但金额只退一部分”在已有规则允许且字段完整时，仍可能是一笔净金额大于零的订单。它不表示商品实际交付或签收情况。

净客单价会随全额退款订单被排除而改变分母，不能单看它判断经营好坏，应同时看支付、退款和订单数。当前计算整个 CSV 的完整订单群，不提供日期、渠道或类别筛选。

## 3. 金额精度与零分母

- 校验模块把 `19.90` 元转成整数 `1990` 分。汇总只有整数加减，没有二进制浮点数累计。
- 客单价使用标准库 `fractions.Fraction` 保存精确的“总分数 ÷ 订单数”，不提前舍入，也不平均各行客单价。
- 展示函数 `format_money` 才按半分阈值四舍五入，再显示元和两位小数。例如 201 分 ÷ 2 笔 = 100.5 分/笔，显示 **1.01 元/笔**。
- 不依赖 `round(float)` 或 Decimal 默认精度；已测试超过 Decimal 默认 28 位有效数字的合法金额仍精确。数据读取和数字长度限制仍由现有校验模块及 Python 约束，不承诺无限大输入。
- 合法文件只有未支付／取消订单时，支付、退款、净额和成交件数均为零，两个客单价显示“无法计算（分母为零）”，商品榜为空。
- 全部订单全额退款时，支付订单数保留，净额和净有效订单数为零；支付客单价可算，净客单价不可算。商品榜保留曾支付过、现在净成交为零的商品。
- 真正空文件或只有表头的文件继续按第二阶段规则拒绝，不把缺少数据伪装成经营结果为零。

## 5. 怎样运行

在 VS Code 打开本项目文件夹，在终端执行：

```powershell
python -B -X utf8 report_metrics.py
```

默认只读 `data/sample_orders.csv`。可传入自己新建的模拟 CSV 路径：

```powershell
python -B -X utf8 report_metrics.py "C:\你的临时目录\模拟订单.csv"
```

`-B` 避免写入 Python 缓存，`-X utf8` 帮助终端显示中文。所有模块只用 Python 标准库，无需安装依赖。只想检查数据时仍使用原有 `validate_orders.py`。

## 7. 开源参考、限制及尚未验证事项

沿用 `开源项目调查.md` 已核实的结论：学习按订单聚合、读取／校验／计算／展示分离的通用思路，不复制候选代码、不引入框架或依赖。已有候选不满足本项目退款与商品明细口径，部分许可不完整或不明确，本轮没有另行引入实现。

本阶段只完成命令行指标计算，暂不提供 GUI、Excel 导入、报表文件导出、图表、AI 日报或数据库。没有自动初始化 Git 或创建提交。

当前仍采用已有的固定状态、类别、渠道及同商品编号单价一致等 V1 校验规则，未经真实平台文件验证，不能直接声称兼容所有电商导出数据。没有支付和退款发生时间，因此只能统计订单状态快照，不能生成实际收款日／退款日流水；净销售额不等于利润。

程序在内存中完整读取、校验和汇总，未做超大文件性能或内存压力测试。汇总随明细数增长，商品排序约为商品种数乘其对数。当前样本仅 80 行；没有为了当前规模加入缓存、并行或外部依赖。

通过测试只证明覆盖的规则和样例得到预期结果，不代表现实业务口径或数据来源永远正确。下一步需先验收当前功能，再决定后续范围。
